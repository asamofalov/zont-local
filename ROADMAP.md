# План развития ZONT WebSocket

Roadmap описывает предполагаемое развитие интеграции после версии `0.2.1`.
Версии задают порядок работ, но не фиксируют календарные сроки.

Обозначения:

- **реализовано** — возможность входит в текущую версию;
- **следующий этап** — основной приоритет разработки;
- **запланировано** — следующий функциональный этап;
- **требует подтверждения протокола** — реализация начнётся только после
  проверки поведения на реальном контроллере и фиксации результата в `docs`.

## v0.2.1 — транспорт WebSocket

Статус: **реализовано**.

- настройка через интерфейс Home Assistant;
- одно авторизованное WebSocket-соединение;
- восстановление соединения после обрыва;
- бинарный сенсор подключения и диагностика;
- повторная авторизация и изменение адреса контроллера;
- универсальные действия `zont_ws.send_command` и `zont_ws.send_bulk`;
- публикация незапрошенных сообщений как событий `zont_ws_event`.

## v0.3 — обнаружение объектов и сущности только для чтения

Статус: **следующий этап**.

- получать список объектов через `req_ids`, а начальные состояния — через
  `req_state`;
- ввести типизированную модель объектов ZONT и единый механизм обновления
  данных;
- использовать входящие сообщения контроллера как push-обновления и выполнять
  контрольный опрос там, где это необходимо;
- создавать `sensor` и `binary_sensor` только для подтверждённых типов:
  температурных и радиодатчиков, аналоговых входов, котлового адаптера,
  состояний и ошибок;
- назначать стабильные `unique_id`, корректно отражать доступность объектов и
  добавлять новые объекты без перезагрузки Home Assistant.

Критерий готовности: поддерживаемые объекты автоматически появляются после
настройки интеграции, получают актуальные состояния и корректно становятся
недоступными при потере связи.

## v0.4 — отопление

Статус: **запланировано**.

- создавать `climate` для подтверждённых контуров отопления `type=16`;
- отображать текущую и целевую температуру, режим работы, неисправность и
  доступность;
- управлять целевой температурой и режимами работы;
- проверять результат команды по состоянию, полученному от контроллера.

Управление температурой и режимами имеет статус
**требует подтверждения протокола**: перед реализацией необходимо проверить
форматы команд, единицы измерения и ответы разных типов контуров на реальном
устройстве.

## v0.5 — исполнительные устройства

Статус: **запланировано**.

- `switch` для реле, насосов и подходящих пользовательских элементов;
- `button` для простых кнопок и безопасных пошаговых действий смесителя;
- `number` для аналоговых регуляторов;
- обновление состояния по ответу контроллера без неподтверждённого
  оптимистичного управления.

Поддержка `alarm_control_panel`, позиционного управления смесителем и других
сложных сущностей имеет статус **требует подтверждения протокола**. Для каждой
такой сущности сначала должны быть подтверждены все состояния, команды и
ошибочные сценарии.

## v0.6 — надёжность и готовность к HACS

Статус: **запланировано**.

- добавить CI для тестов, Ruff, проверки конфигурации Home Assistant, Hassfest
  и HACS;
- поддерживать покрытие автоматическими тестами не ниже 95%;
- расширить безопасную диагностику и использовать Repairs для ошибок, которые
  требуют вмешательства пользователя;
- проверить восстановление после обрывов, перезапуска контроллера и смены
  учётных данных;
- документировать поддерживаемые устройства, ограничения, удаление интеграции
  и устранение неполадок;
- добавить `hacs.json`, обязательные поля manifest, бренд и воспроизводимый
  процесс релизов.

Критерий готовности: проверки HACS и Home Assistant проходят без исключений,
диагностика не раскрывает секреты, а типовые сбои не требуют перезапуска Home
Assistant и не засоряют журнал повторяющимися сообщениями.

## v1.0 — стабильный выпуск

Статус: **запланировано**.

- опубликовать матрицу поддерживаемых контроллеров и прошивок;
- сохранить совместимость действий `zont_ws.send_command` и
  `zont_ws.send_bulk`, конфигурации и идентификаторов сущностей;
- предусмотреть явные миграции для несовместимых изменений;
- подготовить полный пользовательский README и стабильный процесс выпусков
  через HACS;
- считать стабильными только функции, подтверждённые документацией, реальным
  устройством и автоматическими тестами.

## Отложенные возможности

В roadmap намеренно не назначены версии следующим возможностям:

- несколько контроллеров в одной установке Home Assistant;
- автоматическое обнаружение контроллера в локальной сети;
- обновление прошивки из Home Assistant;
- дополнительные терминальные команды `scmd`;
- сущности для неподтверждённых типов и подтипов объектов.

Они будут запланированы после появления подтверждённого протокола или реального
пользовательского сценария. Команды, основанные только на предположениях, не
будут добавляться даже как экспериментальная настройка.

## Принципы развития

- Источники протокола изучаются в порядке, зафиксированном в `AGENTS.md`.
- Предпочтение отдаётся нативным сущностям и жизненному циклу Home Assistant.
- Универсальные действия сохраняются как низкоуровневый совместимый интерфейс.
- Архитектурные решения сверяются с
  [Integration Quality Scale](https://developers.home-assistant.io/docs/core/integration-quality-scale/).
- Подготовка публикации выполняется по
  [требованиям HACS](https://www.hacs.xyz/docs/publish/integration/).
