# ZONT Local для Home Assistant

Пользовательская интеграция Home Assistant для локального WebSocket-интерфейса
контроллера ZONT. Она поддерживает одно авторизованное соединение, создаёт
сущности подключения и диагностики контроллера, обнаруживает аналоговые входы,
адаптеры цифровой шины котла, проводные температурные датчики и подтверждённые
типы радиодатчиков, насосы, смесители, реле и контуры отопления, умеет передавать
температуру из Home Assistant в цифровые датчики ZONT, публикует входящие
сообщения как события Home Assistant и предоставляет действия для универсальных
команд ZONT.

Планы развития интеграции описаны в [ROADMAP.md](./ROADMAP.md), а границы
компонентов и жизненный цикл — в [docs/ARCHITECTURE.md](./docs/ARCHITECTURE.md).

## Требования

- Home Assistant 2026.8 или новее;
- локальный IPv4- или IPv6-адрес контроллера ZONT;
- имя пользователя и пароль контроллера.

## Установка

1. Скопируйте каталог `custom_components/zont_local` в
   `/config/custom_components/zont_local` вашего Home Assistant.
2. Перезапустите Home Assistant.
3. Откройте **Настройки → Устройства и службы → Добавить интеграцию**.
4. Выберите **ZONT Local**, укажите IP-адрес и учётные данные контроллера.
5. Выберите режим ZONT, который отключает все контуры ГВС и потребительские
   контуры.
6. Выберите устройства ZONT, которые нужно импортировать в Home Assistant.

Интеграция принимает именно IP-адрес, без протокола, порта и пути. Адрес
локального WebSocket-интерфейса `ws://<IP>/ws` формируется автоматически.

При добавлении интеграция запрашивает у контроллера серийный номер, модель,
модель платы и версию прошивки. Серийный номер используется как стабильный
идентификатор, поэтому ответы на команды `#S54?` и `#S7?` обязательны для
завершения настройки.

На втором шаге интеграция показывает только режимы, в которых каждый
обнаруженный контур ГВС и потребительский контур имеет нулевую уставку и
указывает этот режим в своём списке применимых режимов. Название режима может
быть любым: назначение определяется по конфигурации, а не по словам вроде
«Выключен». Если подходящего режима нет, настройте его в ZONT и повторите
добавление интеграции. На этом же шаге задаются температура включения ГВС и
интервал контрольного полного опроса контроллера.

На третьем шаге отображаются поддерживаемые интеграцией объекты в формате
`Тип устройства - Название (ID)`. По умолчанию выбраны все найденные объекты и
включён автоматический импорт новых. Сам контроллер и его общие сущности
добавляются всегда, поэтому список можно оставить пустым.

Объекты, для которых контроллер вернул `failed=1` вместо текущего состояния,
пропускаются при первоначальном выборе режима. Если такой контур позднее станет
доступным, интеграция включит его в повторную проверку и не предложит управление
включением и выключением, пока выбранный режим не будет безопасен для всех
доступных контуров.

## Переход с ZONT WebSocket до версии 0.10.3

Версия 0.11.0 переименовывает интеграцию и меняет технический домен с
`zont_ws` на `zont_local`. Автоматической миграции и совместимых псевдонимов
для прежних действий и события нет.

Перед заменой файлов выполните следующие действия:

1. Пока старая версия ещё установлена, удалите её запись в разделе
   **Настройки → Устройства и службы**.
2. Остановите Home Assistant.
3. Удалите каталог `/config/custom_components/zont_ws` и установите вместо
   него `/config/custom_components/zont_local`.
4. Запустите Home Assistant и добавьте **ZONT Local** заново.
5. Повторно настройте импорт и экспорт устройств.
6. Замените в автоматизациях `zont_ws.send_command` и `zont_ws.send_bulk` на
   `zont_local.send_command` и `zont_local.send_bulk`, а `zont_ws_event` — на
   `zont_local_event`.

Автоматически создаваемые entity ID могут совпасть с прежними благодаря тем же
именам устройств, но интеграция этого не гарантирует. Пользовательские имена,
области и другие настройки удалённых записей при повторном добавлении не
восстанавливаются.

После настройки модель и версия прошивки обновляются в фоне при запуске и после
восстановления соединения. Последние полученные значения сохраняются в Home
Assistant, поэтому обновление сведений не задерживает загрузку интеграции.

Через действие **Перенастроить** в настройках интеграции можно изменить
IP-адрес, имя пользователя и пароль. Если пароль менять не требуется, оставьте
поле нового пароля пустым. Эти параметры принадлежат самому соединению, поэтому
после их изменения интеграция штатно заменяет WebSocket-клиент и заново
подключается к контроллеру.

Через действие **Настроить** доступны три раздела. В **Основных настройках**
можно повторно выбрать режим отключения, задать температуру включения ГВС после
перезапуска Home Assistant и изменить интервал контрольного опроса. По
умолчанию используются `60 °C` и `60 секунд`. Интервал можно установить от `10`
до `120 секунд`; малые значения увеличивают количество запросов к контроллеру.
Основные настройки, импорт устройств и экспорт сущностей применяются без
перезагрузки записи интеграции и без разрыва текущего WebSocket-соединения.

В разделе **Импорт устройств** можно добавить или исключить дочерние устройства
и включить автоматический импорт новых объектов. Явно исключённый объект не
будет добавлен повторно даже при включённом автоимпорте. Новый объект — это ID,
который ещё не был выбран или исключён пользователем.

Исключение удаляет дочернее устройство и его сущности из реестров Home
Assistant. При повторном импорте сохраняются стабильные `unique_id`, но
пользовательские имена, области и другие настройки удалённых записей
автоматически не восстанавливаются. Протокольный опрос продолжает получать
данные всех поддерживаемых объектов независимо от выбора импорта. При изменении
выбора остальные устройства не выгружаются и не становятся недоступными.

В разделе **Экспорт в ZONT** можно передавать показания температурных сенсоров
и состояния любых `binary_sensor` Home Assistant. Температуры записываются в
цифровые датчики ZONT `type=1`, а бинарные состояния — в виртуальные дискретные
входы `type=0`. Для каждой привязки доступны два варианта:

- создать новый датчик в ZONT с указанным названием;
- выбрать существующий датчик ZONT, например уже используемый автоматизацией.

При привязке существующего датчика интеграция показывает его название и ID и
перед сохранением явно предупреждает о первой записи. Для температуры
источником может быть только `sensor` с классом устройства `temperature` и
поддерживаемой единицей измерения. Значение преобразуется в градусы Цельсия и
округляется до `0,1 °C`. Для бинарного экспорта поддерживается любой внешний
`binary_sensor`, в том числе без `device_class`. При создании объекта нужно
явно выбрать тип входа: НР (`stype=19`) или НЗ (`stype=20`). Интеграция всегда
передаёт состояние `off` командой `0 0 180`, а `on` — командой `0 20 180`.
Поэтому для НР сработкой ZONT является `off`, а для НЗ — `on`.

Новое значение отправляется сразу после изменения состояния. Общая контрольная
запись для всех привязок выполняется каждые `120 секунд` и после восстановления
соединения. Если источник недоступен, интеграция прекращает запись; виртуальный
дискретный вход ZONT самостоятельно станет недоступным после тайм-аута
`180 секунд`.

Цель экспорта автоматически исключается из обычного импорта устройств ZONT,
чтобы не создавать в Home Assistant обратную копию того же значения. При
удалении привязки сам датчик из контроллера не удаляется и остаётся исключённым.
Если цель была удалена или перестала соответствовать типу привязки, интеграция
не пересоздаёт её автоматически и показывает проблему в разделе устранения
неполадок Home Assistant. Добавление, изменение и удаление привязок сразу
перенастраивает менеджер экспорта на существующем общем соединении.

Автоматизацию с `zont_local.send_command` или `zont_local.send_bulk` можно
использовать и после настройки встроенного экспорта. После привязки её датчика
в разделе экспорта автоматизацию лучше отключить, чтобы два механизма не
записывали значение одновременно.

## Сущности контроллера

Интеграция добавляет к устройству ZONT следующие сущности:

- **Подключение** — состояние локального WebSocket-соединения;
- **Связь с облаком** — состояние облачного подключения по данным
  `#S224?`;
- **Канал связи** — все активные каналы GSM, Wi‑Fi и Ethernet по данным
  `#S224?`;
- **Напряжение питания** — значение `#S6?` в вольтах;
- **Источник питания** — основное питание или батарея по данным `#S6?`;
- **Подключение Wi‑Fi** — фактическая связь с точкой доступа по данным
  `#S198?`;
- **Подключение Ethernet** — состояние проводного интерфейса по данным
  `#S205?`, если команда поддерживается контроллером;
- **Регистрация GSM** — домашняя сеть, поиск сети, отказ, роуминг или отсутствие
  регистрации по данным `#S4?`;
- **Уровень сигнала Wi‑Fi** и **Уровень сигнала GSM** — диагностические сенсоры
  в процентах, отключённые по умолчанию;
- **Перезагрузить** — кнопка отправки команды `SRESTART?`.

Необязательные сущности создаются только после первого корректного ответа
контроллера. Например, ответ `#S205:!` означает, что Ethernet-диагностика на
данной модели не поддерживается, поэтому соответствующая сущность не появится.
Это не считается ошибкой и не влияет на остальные обновления.

Проценты Wi‑Fi рассчитываются из передаваемого контроллером положительного
модуля RSSI по шкале от `−100` до `−50 dBm`. Уровень GSM `0…31` переводится в
проценты относительно максимального значения `31`. Эти два показателя имеют
разные исходные шкалы и не предназначены для прямого сравнения. Чтобы включить
их, откройте отключённые сущности устройства ZONT в Home Assistant.

MAC-адрес, IP-адрес, маска, шлюз и название мобильного оператора из системных
ответов не сохраняются в состоянии сущностей и не включаются в скачиваемую
диагностику.

Сведения о модели запрашиваются после каждого подключения, а изменяемые
показатели контроллера — с настроенным интервалом контрольного опроса. Первый
опрос выполняется в фоне и не задерживает загрузку интеграции. При
восстановлении WebSocket-соединения данные обновляются сразу.

Кнопка **Перезагрузить** перезапускает физический контроллер. Интеграция не
разрывает WebSocket сама: диагностические сущности становятся недоступными,
когда контроллер фактически закрывает соединение, и восстанавливаются
автоматически после его запуска.

Общий диагностический binary sensor **Неисправность** создаётся только для
объектов с подтверждённым протокольным признаком аварии. Временная
недоступность, остановленный насос или обычная сработка входа не считаются
неисправностью устройства и отображаются штатными состояниями Home Assistant.

## Аналоговые входы

Интеграция обнаруживает аналоговые входы `type=0` и создаёт для каждого из них
отдельное дочернее устройство с именем из настроек ZONT. Модель устройства
соответствует назначенному в контроллере подтипу: датчику давления, движения,
протечки, влажности, дискретному входу или другому документированному пресету.

Для каждого входа создаются две сущности:

- **Значение** — числовое поле `v` с единицей, которую передал контроллер;
- **Сработка** — бинарное состояние поля `trig` с подходящим классом устройства
  Home Assistant.

Для дискретных и охранных входов основным состоянием является **Сработка**.
Их сырое числовое **Значение** создаётся как отключённая по умолчанию
диагностическая сущность и при необходимости включается в настройках
устройства. У измерительных входов обе сущности включены по умолчанию.

Поддерживаются все документированные подтипы `stype=0…21` и единицы: вольты,
килоомы, бары, километры в час, обороты в минуту, литры, литры в час и проценты.
Неизвестный подтип безопасно отображается как универсальный аналоговый вход.
Если контроллер не передал отдельное поле, соответствующая сущность остаётся
недоступной. При `a=0` обе сущности становятся недоступными, сохраняя последние
полученные значения до восстановления входа.

## Адаптеры цифровой шины

Интеграция обнаруживает адаптеры цифровой шины `type=6` и создаёт для каждого
из них отдельное дочернее устройство с именем, заданным в ZONT. Доступные
показатели запрашиваются с настроенным интервалом контрольного опроса и
обновляются сразу при получении WebSocket-сообщения от контроллера.

Для адаптера создаются только те сущности, значения которых контроллер
фактически передал:

- **Температура теплоносителя**;
- **Температура ГВС**;
- **Температура обратки**;
- **Модуляция**;
- **Давление теплоносителя**;
- **Состояние** — «Выключен», «Работает» или «Ошибка»;
- **Код ошибки**;
- **Неисправность** — диагностический binary sensor с классом `problem`.

Неисправность считается активной, если поле `state` содержит состояние
«Ошибка» или `err` содержит ненулевой код. Сущность появляется после первого
ответа хотя бы с одним из этих полей и не создаётся по одной только
недоступности адаптера.

Температура обратки, модуляция и давление предусмотрены протоколом, но могут не
поддерживаться конкретным котлом или адаптером. В таком случае лишние сущности
не создаются. При временной недоступности адаптера уже созданные сущности
становятся недоступными и восстанавливаются автоматически.

## Температурные датчики

Цифровые датчики `type=1` и NTC-термодатчики `type=27` создаются как отдельные
дочерние устройства контроллера с именами из настроек ZONT. Для каждого объекта
интеграция добавляет сенсор температуры в градусах Цельсия. Например, объект с
именем `Т Спальня` получает сущность `sensor.t_spalnia_temperature`.

Поле `a` из ответа контроллера определяет доступность датчика. При временном
отключении последнее значение сохраняется, но сущность становится недоступной
до восстановления датчика. Поле `trig` для температурных датчиков пока не
используется, поскольку его назначение для `type=1` и `type=27` не подтверждено
документацией.

## Насосы

Интеграция обнаруживает насосы `type=17` и создаёт для каждого отдельное
дочернее устройство с именем из настроек ZONT. Основной `binary_sensor` с
классом `running` показывает фактическую работу насоса по полю `s`: `0` — насос
не работает, `1` — работает. Состояние обновляется сразу по push-сообщениям и
проверяется во время общего контрольного опроса.

Управление насосом из Home Assistant не предоставляется. Контроллер учитывает
запросы контуров и настроенный выбег: принятая команда выключения не означает,
что насос физически остановится сразу или остановится при активном запросе.
Поэтому интеграция отображает только фактическое состояние и не подменяет его
оптимистично.

## Смесители

Интеграция обнаруживает смесители `type=15` и создаёт для каждого отдельное
дочернее устройство с именем из настроек ZONT. Основной enum-сенсор показывает
состояния **В покое**, **Открывается**, **Закрывается**, **Полностью открыт** и
**Полностью закрыт**.

Направление движения берётся из оперативного поля `s` WebSocket-состояния.
Концевые положения и диагностические флаги читаются командой `#Y<id>?` во
время настроенного контрольного опроса через то же WebSocket-соединение. После
начала движения прежнее концевое положение сразу сбрасывается, чтобы после
остановки не показывать устаревший предел до следующей контрольной сверки.

Для смесителя также создаются общий диагностический binary sensor
**Неисправность** и подробные сенсоры **Неисправность датчика**,
**Неисправность выхода** и **Ошибка установки**. Общий признак включается при
наличии любой из трёх перечисленных ошибок.
Если внутреннее состояние временно не удалось прочитать, оперативное движение
продолжает отображаться, а остановленное положение и диагностические сенсоры
становятся недоступными до следующего успешного опроса. Одновременно
установленные признаки полностью открытого и полностью закрытого положения
считаются противоречивыми и не отображаются как достоверное состояние.

Управление смесителем из Home Assistant не предоставляется: безопасные
команды позиционного управления и их ошибочные сценарии пока не подтверждены.

## Реле

Интеграция обнаруживает реле `type=14` и создаёт для каждого отдельное дочернее
устройство с именем из настроек ZONT. Основная сущность `switch` показывает и
изменяет логическое состояние реле. Публикуются все объекты этого типа, в том
числе реле без выбранного аппаратного выхода (`255`).

Физическое поле `s` сопоставляется с логическим состоянием с учётом настройки
**Инверсный режим** из `#Z<id>?`. Контроллер использует два исторически
дублирующих бита инверсии со значениями `1` и `8`; наличие любого из них
инвертирует `s`. Если конфигурацию прочитать не удалось, переключатель остаётся
недоступным, чтобы не отправить команду с ошибочной логической семантикой.

Включение и выключение отправляются как `cmd=1` и `cmd=0`. После `cmdres=0`
интеграция адресно перечитывает состояние и не обновляет сущность оптимистично.
Из регистра `#Y<id>?` также создаётся диагностический binary sensor
**Неисправность**. Ошибка чтения этого регистра не мешает работе переключателя:
недоступной становится только диагностика.

## Радиодатчики

Интеграция обнаруживает радиодатчики `type=8` и создаёт отдельные дочерние
устройства для пяти подтипов, чтение которых подтверждено документацией:

- `stype=5` — радиотермометр: температура, напряжение батареи и уровень
  сигнала;
- `stype=10` — радиодатчик протечки: сработка, напряжение батареи и уровень
  сигнала;
- `stype=11` — радиодатчик движения: движение, напряжение батареи и уровень
  сигнала;
- `stype=15` — внешний радиодатчик температуры: температура, напряжение батареи
  и уровень сигнала;
- `stype=18` — радиодатчик температуры и влажности: температура, влажность,
  напряжение батареи и уровень сигнала.

Напряжение батареи отображается в вольтах, а уровень радиосигнала — в dBm; обе
сущности относятся к диагностике и включены по умолчанию. Набор сущностей
фиксирован подтипом, поэтому временно отсутствующее поле не меняет структуру
устройства: только соответствующая сущность становится недоступной. При `a=0`
недоступным становится весь радиодатчик, а последние корректные значения
сохраняются до восстановления.

Остальные документированные и неизвестные подтипы безопасно принимаются
протокольным слоем, но пока не создают устройств и сущностей. Управление
радиореле, розетками, панелями и брелоками в этой версии не реализовано.
Поддержка обычных реле `type=14` не распространяется на эти радиоустройства.

## Контуры ГВС

Интеграция обнаруживает контуры отопления `type=16` и создаёт отдельное
дочернее устройство и сущность `water_heater` для каждого контура ГВС
`stype=1`. Имя устройства берётся из настроек ZONT.

Сущность показывает текущую температуру `c`, целевую температуру `s` и
позволяет изменить уставку. Команда передаётся контроллеру в децикельвинах,
после подтверждения выполняется адресное чтение состояния. Интеграция не
подменяет значение оптимистично: в Home Assistant отображается уставка,
которую фактически вернул контроллер.

Для каждого контура ГВС также создаётся включённый по умолчанию диагностический
binary sensor **Неисправность** с классом `problem`. Он использует поле `f`
WebSocket-состояния и становится недоступным, если контроллер не передал этот
флаг или весь контур недоступен.

Основной binary sensor **Нагрев** показывает фактическую активность контура по
биту `1` внутреннего состояния `#Y`. Значение не вычисляется сравнением текущей
температуры с уставкой: контроллер самостоятельно учитывает гистерезис,
задержки и инерцию системы. Если внутреннее состояние временно не прочитано,
сенсор нагрева становится недоступным независимо от основной сущности ГВС.

Используется диапазон `5–75 °C` с шагом интерфейса `1 °C`. Применимые
именованные режимы ZONT представлены штатными operation modes Home Assistant
в порядке из `#Y`. В список входят режимы с нулевой уставкой, а последним
добавляется **Ручной режим**. Повторяющиеся названия различаются по ID по тем же
правилам, что и presets потребительских контуров.

При `m_id>0` состоянием сущности становится пользовательское название режима,
включая режим с нулевой уставкой. При `m_id=0` и активном ГВС отображается
**Ручной режим**. Если конфигурация режима временно неизвестна, интеграция
безопасно возвращается к состояниям `on` и `off`; без применимых режимов
сохраняется прежнее поведение.

Выбор operation mode применяет его только к указанному контуру ГВС и проверяет
`cmdres`, фактический `m_id` и итоговое состояние. Выбор **Ручного режима**
повторно отправляет последнюю корректную уставку, а при её отсутствии —
настроенную температуру включения, и требует подтверждения `m_id=0`.
Оптимистичное обновление не используется.

> **Изменение состояния в v0.10.1:** при активном именованном режиме state
> сущности меняется с `on` на название ZONT, например `Комфорт`. Автоматизации,
> которые сравнивают состояние `water_heater` со строкой `on`, необходимо
> обновить.

При стандартном отключении выбранный режим с нулевыми уставками применяется
только к указанному контуру ГВС. Интеграция не применяет его ко всему
контроллеру.

Перед отключением интеграция запоминает действующую уставку ГВС в памяти и при
включении восстанавливает её. После перезапуска Home Assistant этот кэш пуст,
поэтому уже выключенный контур включается на температуру из настроек интеграции
(`60 °C` по умолчанию). Команды включения и отключения считаются успешными
только после `cmdres=0` и адресного подтверждения фактического состояния;
оптимистичное обновление не используется. Стандартное включение восстанавливает
ручную температуру, а не предыдущий именованный режим.

Остальные подтипы контуров сохраняются во внутренней модели, но пока не создают
устройств и сущностей.

## Потребительские контуры

Для каждого потребительского контура `type=16`, `stype=3` интеграция создаёт
отдельное дочернее устройство и основную сущность `climate`. Имя устройства
берётся из настроек ZONT. Сущность показывает текущую температуру `c`, уставку
`s` и наблюдаемое состояние `m`. Штатное поле `hvac_action` отдельно показывает
фактическую работу: `heating` при запросе тепла и `idle` при ожидании. После
выбора проверенного режима отключения сущность предоставляет стандартные режимы
Home Assistant **Нагрев** и **Выключено**, а также действия `climate.turn_on`
и `climate.turn_off`.

При отключении интеграция применяет выбранный режим только к указанному
контуру, поэтому остальные контуры не изменяются. Команда считается успешной
только после `cmdres=0` и адресного подтверждения фактического `m_id` и
состояния `off`.

Перед отключением интеграция запоминает последний активный режим и уставку в
памяти. При включении сначала восстанавливается прежний именованный режим, если
он по-прежнему применим, затем прежняя ручная уставка, а в крайнем случае —
минимальная допустимая температура. Этот кэш не сохраняется между перезапусками
Home Assistant, поэтому уже выключенный при запуске контур включается на
минимальной допустимой уставке.

Целевую температуру можно изменять с шагом интерфейса `1 °C`. Команда
передаётся контроллеру в децикельвинах и после подтверждения проверяется
адресным чтением состояния. Установка разрешена и для выключенного контура:
переход в ручной режим и итоговое состояние определяет сам контроллер,
оптимистичное обновление в Home Assistant не применяется.

Допустимый диапазон определяется из внутренней конфигурации ZONT:

- управление по воздуху или по воздуху с ПИД использует пороги активного
  датчика, а при отсутствии отдельных порогов — `5–40 °C`;
- управление по теплоносителю без ПЗА или с флагом request-only использует
  настроенные границы контура, затем пороги активного датчика и крайний запасной
  диапазон `−30…100 °C`;
- управление по теплоносителю с ПЗА использует воздушную уставку `5–35 °C`.

Конфигурация обновляется после подключения, при появлении нового контура и по
уведомлению контроллера `CFG_RELOAD_REQ`; активный датчик проверяется во время
каждого контрольного опроса. Последний корректный диапазон сохраняется при
временной ошибке. Если конфигурация неизвестна или небезопасна для прямого
управления — например, это зависимый контур либо внешний термостат без ПЗА —
сущность остаётся доступной только для чтения.

Устройство потребительского контура также содержит основные сущности
**Расчётная температура теплоносителя** и **Летний режим**. Температура берётся
из поля `0` ответа `#Y`, переводится из децикельвинов и показывается независимо
от наличия ПЗА и способа регулирования. Если выключенный контур сохраняет
последнее расчётное значение, интеграция показывает его без собственной
очистки. Летний режим отражает текущее применение ограничения, а не наличие
этой настройки в конфигурации.

Включённые по умолчанию диагностические сущности показывают способ
регулирования, наличие погодозависимой автоматики, блокировку контура,
неисправность датчика и общую неисправность. Способ регулирования и ПЗА
определяются из `#Z`; блокировка и неисправность датчика — из битовой маски
`#Y`; общая неисправность — из поля `f` WebSocket-состояния. Если отдельный
источник не получен, зависящие от него состояния становятся недоступны
независимо от основной сущности `climate`.

Применимые именованные режимы ZONT представлены штатными presets Home
Assistant. Список строится по данным `#Y` и конфигурациям `#Z type=20` в
порядке, который сообщил контроллер. В него входят и режимы с нулевой уставкой:
так можно различить, например, выключение контура режимами **Лето** и
**Выключен**. При `m_id=0` контур считается управляемым вручную и активный
preset не показывается.

Названия берутся из ZONT без переименования. Если несколько применимых режимов
имеют одинаковое название, интеграция добавляет к конфликтующим вариантам ID,
например `Комфорт (20501)`. Выбор preset применяет режим только к этому
контуру, проверяет `cmdres`, фактический `m_id` и итоговое состояние без
оптимистичного обновления. Presets доступны независимо от прямой регулировки
температуры и настройки стандартных действий включения и отключения.

Состав и названия режимов обновляются после переподключения или перезагрузки
интеграции. Редкое фоновое обновление конфигурации без переподключения
запланировано для следующего этапа.

## Действия

### `zont_local.send_command`

Отправляет одну команду. Обязательные поля: `id` от 0 до 999999 и непустое
значение `cmd`. Если запрошен ответ действия, результат имеет следующий вид:

```yaml
response: <декодированный ответ ZONT>
```

### `zont_local.send_bulk`

Последовательно отправляет непустой список команд и останавливается при первой
ошибке. Если запрошен ответ действия, результат имеет следующий вид:

```yaml
responses:
  - id: 4107
    response: <декодированный ответ ZONT>
```

При запуске Home Assistant интеграция ожидает подключения и авторизации не
более пяти секунд. Если контроллер недоступен, Home Assistant откладывает
загрузку интеграции и повторяет попытку штатным механизмом. До первого успешного
подключения бинарный сенсор подключения недоступен.

После успешной загрузки последующие обрывы уже не задерживают Home Assistant:
бинарный сенсор переходит в состояние «Выключено», а интеграция восстанавливает
соединение в фоне с увеличивающейся задержкой до 30 секунд. Диагностические
сущности на время обрыва становятся недоступными. Действия сразу завершаются
ошибкой; после восстановления сенсор снова переходит в состояние «Включено», а
данные контроллера запрашиваются заново.

При штатной остановке или перезапуске Home Assistant ожидаемое закрытие
WebSocket не считается потерей связи. Интеграция сохраняет последние корректные
состояния и не добавляет в историю массовый переход сущностей в состояние
«Недоступно» непосредственно перед остановкой.

Команды состояния контроллера `#S224?`, `#S6?`, `#S198?`, `#S205?` и `#S4?`
выполняются во время каждого настроенного контрольного опроса. Ответ `!` и
ошибка формата относятся только к текущему циклу: следующий опрос повторяет
команду. Если ответ не пришёл за пять секунд, интеграция закрывает соединение,
чтобы запоздавший ответ не был принят за результат следующего запроса, а после
переподключения выполняет один объединённый полный опрос.

## События

Входящие сообщения, не являющиеся ответами на команды, публикуются как событие
`zont_local_event`:

```yaml
device_id: <идентификатор устройства Home Assistant>
payload: <декодированное значение JSON или исходный текст>
```

## Разработка

Откройте репозиторий в VS Code и выполните команду **Dev Containers: Reopen in
Container**. Контейнер автоматически установит закреплённые зависимости и
подключит интеграцию к локальной конфигурации Home Assistant.

Проверки внутри контейнера:

```bash
python -m pytest -q
ruff check .
ruff format --check .
python -m homeassistant --script check_config --config .devcontainer/config
```

Запуск тестового Home Assistant на порту 8123:

```bash
python -m homeassistant --config .devcontainer/config
```
