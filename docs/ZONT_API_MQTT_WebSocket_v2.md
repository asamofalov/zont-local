# ZONT API: MQTT и WebSocket

Техническая документация, версия 2.

Markdown-версия документа
[«ZONT_API_MQTT_WebSocket_v2.pdf»](./ZONT_API_MQTT_WebSocket_v2.pdf).

Основа документа: официальный PDF «Формат обмена сообщениями с контроллерами
ZONT через JSON», MQTT-документация ZONT, а также наблюдаемые ответы конкретного
контроллера. Сведения из практических наблюдений отмечены отдельно.

## 1. Архитектура и область применения

WebSocket API предназначен для прямого JSON-обмена с контроллером. Состояния
объектов и команды управления используют ту же модель данных, что и
MQTT-протокол ZONT. Это позволяет строить локальные интеграции, в том числе для
Home Assistant, без промежуточного облачного API.

```text
Home Assistant / локальная интеграция
  |
  | WebSocket JSON
  v
ZONT controller
  +-- внутренние объекты: датчики, реле, насос, контуры
  +-- MQTT client -> внешний MQTT broker, если функция доступна
  +-- облачный канал ZONT
```

Наличие MQTT-клиента и возможность его настройки зависят от модели и прошивки.
WebSocket API документирован отдельно и не означает автоматического наличия
пользовательской настройки MQTT.

## 2. WebSocket API

### 2.1. Адрес подключения

```text
ws://<ip-address>/ws
wss://<ip-address>/ws
```

В официальном документе адрес записан как HTTP/HTTPS URL, однако транспортом
является WebSocket; в клиентских библиотеках используются схемы `ws://` и
`wss://`.

### 2.2. Авторизация

```json
{
  "user": "user_name",
  "pass": "user_password"
}
```

Успешный ответ:

```json
{"auth": 200}
```

Ошибка авторизации:

```json
{"auth": 401}
```

Используются имя и пароль пользователя из настроек пользователей контроллера.

### 2.3. Получение списка ID объектов

```json
{"req_ids": 16}
```

Ответ:

```json
{"ids": [20494, 20496, 8362]}
```

Поле `req_ids` соответствует типу объекта в конфигурации. Для запроса объектов
любого поддерживаемого типа официальный документ указывает `req_ids=255`.

На исследованном контроллере запрос `{"req_ids": 255}` вернул полный список из
41 ID. Ответ не содержит типы объектов или границы между группами, поэтому его
одного недостаточно для классификации объекта, если последующий `req_state`
завершается ошибкой.

При отправке восьми типизированных запросов одним блоком подтверждаемые ответы
пришли в порядке запросов. Это наблюдаемое FIFO-поведение конкретного
контроллера, но не документированная гарантия протокола. Клиенту безопаснее
выполнять типизированные `req_ids` последовательно.

### 2.4. Запрос состояния

```json
{"id": 20496, "req_state": 0}
```

Ответ содержит `id`, `type`, `name` и набор полей, зависящий от типа объекта.
Официальная спецификация указывает, что поля состояния совпадают с полями
MQTT-протокола ZONT.

Если состояние конкретного объекта получить нельзя, контроллер может ответить:

```json
{"id": 20494, "req_state": 0, "failed": 1}
```

Такой ответ означает недоступность объекта, а не потерю WebSocket-соединения.

### 2.5. Управление объектом

```json
{"id": 20496, "cmd": 3130}
```

Ответ:

```json
{"id": 20496, "cmdres": 0}
```

`Command` имеет тот же формат, что команда `cmd` в MQTT. В WebSocket
дополнительно указывается `id` объекта.

### 2.6. Управление устройством и терминальные команды

```json
{"scmd": "#S7?"}
```

Ответ:

```json
{"scmdres": "#S7:H2000PRO…"}
```

Это единственный конкретный пример системной команды, явно приведённый в
официальном документе JSON API. Другие `#S`-команды ниже отмечены как
наблюдаемые на реальном устройстве, а не как полный официальный справочник.

| `type` | Официальное описание |

| `0` | Аналоговый вход |

| `2` | Охранная зона |
| `6` | Адаптер цифровой шины |

| `15` | Смеситель |
| `16` | Контур отопления |
| `17` | Насос |
| `27` | NTC-термодатчик |

В конфигурациях конкретных устройств могут встречаться дополнительные

и `type=21`. Они отсутствуют в предоставленной официальной таблице WebSocket
API и поэтому не включены в неё.

## 5. Поля состояния объектов

Набор полей зависит от `type` и `stype`. Ниже приведены поля, подтверждённые
предоставленными протоколами и наблюдаемыми ответами контроллера.

| Поле | Смысл | Применение |
| --- | --- | --- |
| `id` | Идентификатор объекта | Все объектные ответы |
| `type` | Тип объекта | Все объектные ответы |
| `stype` | Подтип | Часть типов: 0, 8, 10 и 16 |
| `name` | Имя объекта | Большинство объектов |
| `t` | Температура | Температурные датчики |
| `v` | Значение аналогового входа | `type=0` |
| `a` | Активность или доступность | Датчики и входы |
| `trig` | Состояние триггера | Датчики и входы |
| `c` | Текущее значение или температура контура | `type=16`; смысл зависит от `stype` |
| `s` | Уставка контура | `type=16` |
| `m` | Текущий режим, наблюдаемое поле | `type=16` |
| `m_id` | ID режима, наблюдаемое поле | `type=16` |
| `f` | Флаг или состояние, зависит от объекта | Несколько типов |
| `water` | Температура теплоносителя | `type=6`, адаптер котла |
| `dhw` | Температура ГВС | `type=6` |
| `state` | Состояние адаптера | `type=6` |
| `err` | Код ошибки | `type=6` |

### 5.1. Примеры реальных ответов

Цифровой датчик температуры:

```json
{
  "id": 8196,
  "type": 1,
  "name": "Погода из интернета",
  "t": 9.9,
  "a": 1,
  "trig": 0
}
```

Контур отопления:

```json
{
  "id": 20496,
  "type": 16,
  "stype": 3,
  "name": "Отопление",
  "m": "heat",
  "m_id": 20501,
  "c": 36.0,
  "s": 41.0,
  "f": 0
}
```

В наблюдаемом WebSocket-ответе контура значения `c` и `s` уже представлены в
градусах Цельсия. Нельзя автоматически считать все поля `c` и `s`
децикельвинами только по их имени. Единицы необходимо определять по типу
сообщения и MQTT-описанию.

Адаптер цифровой шины котла:

```json
{
  "id": 4097,
  "type": 6,
  "name": "Navien",
  "water": 36.0,
  "dhw": 35.0,
  "state": 0,
  "err": 0
}
```

## 6. MQTT и соответствие WebSocket

Официальная WebSocket-спецификация отсылает к MQTT-протоколу для содержимого
`state` и `Command`. Объектная семантика общая, а транспорт различается.

| Операция | MQTT | WebSocket |
| --- | --- | --- |
| Чтение состояния | Публикации по топикам протокола | `{"id": id, "req_state": 0}` |
| Управление объектом | `cmd` в MQTT | `{"id": id, "cmd": Command}` |
| Результат команды | Ответ или публикация MQTT | `{"id": id, "cmdres": res}` |
| Системная команда | Не является базовой объектной командой | `{"scmd": "#S..."}` |

### 6.1. Температурные команды и DK

В MQTT-документации часть температурных команд задаётся в децикельвинах
(`0,1 K`):

```text
DK = round((°C + 273.0) * 10)
°C = DK / 10 - 273.0
```

Пример:

```text
40.0 °C -> 3130 DK
```

Не следует применять DK к каждому температурному полю ответа: в
WebSocket-state конкретного контроллера часть температур приходит уже в
градусах Цельсия.

## 7. Терминал и `scmd`

Официально подтверждён механизм `scmd` и пример `#S7?`. Остальные команды в
таблице были фактически зафиксированы в предоставленной WebSocket-сессии и не
образуют полный терминальный справочник.

| Команда | Статус источника | Наблюдаемый смысл |
| --- | --- | --- |
| `#S7?` | Официальный пример API | Идентификация и информация об устройстве |
| `#S4?` | Зафиксировано в сессии | Параметры GSM и оператора |
| `#S198?` | Зафиксировано в сессии | Сетевые и Wi-Fi данные |
| `#S205?` | Зафиксировано в сессии | Сетевой параметр; ответ `#S205:!` |
| `#S208?` | Зафиксировано в сессии | Wi-Fi credentials/status; содержит чувствительные данные |

Команды вроде `#R`, `#TIME?`, `#LOG?`, `#S250` и другие намеренно не включены:
предоставленные официальные документы и логи их не подтверждают.

Ответ `scmdres` не содержит отдельного идентификатора запроса. Системные
команды следует выполнять последовательно. Незапрошенные и диагностические
ответы нельзя без фильтрации публиковать в событиях или журнале: `#S54`,
`#S198`, `#S208` и `#S213` могут содержать идентификаторы устройства, сетевые
параметры, Wi-Fi credentials и данные SIM.

## 8. Рекомендуемая схема интеграции Home Assistant

```text
HA custom component
  +-- connect ws(s)://zont/ws
  +-- auth {user, pass}
  +-- req_ids(type)
  +-- req_state(id)
  +-- maintain object registry by id
  +-- push state changes into HA entities
  +-- send {id, cmd} for writes
  +-- optional scmd service for diagnostics
```

Для первой версии интеграции целесообразно поддержать:

- `type=1` и `type=27` как `sensor`;
- `type=14` как `switch`;
- `type=16` как `climate` или `sensor` в зависимости от `stype`;
- `type=6` как набор диагностических `sensor`;
- `type=17` как `switch` или fan-like entity после проверки фактических полей
  состояния.

## 9. Практические замечания

| Тема | Рекомендация |
| --- | --- |
| Reconnect | При обрыве WebSocket выполнять экспоненциальное переподключение и повторную авторизацию |
| Bootstrap | Объединить полный список `req_ids=255` с последовательными запросами поддерживаемых типов, затем выполнить `req_state` каждого ID |
| Push | Использовать push для оперативных изменений, а `req_state` — для bootstrap и контрольной перепроверки; веб-интерфейс опрашивает состояния примерно каждые 30–60 секунд |
| Unknown fields | Сохранять неизвестные поля для диагностики или атрибутов, не отбрасывать при парсинге |
| Routing | Разделять `cmdres`, `ids`, `scmdres` и состояния; один только совпавший `id` не доказывает, что получен ответ команды |
| Timeout | После таймаута запроса переподключаться, чтобы поздний ответ не был сопоставлен со следующим запросом |
| `cmdres` | Коррелировать результат команды по `id` или `Id` и обязательному `cmdres`; не считать запись успешной только по факту отправки кадра |
| `scmdres` | Выполнять `scmd` последовательно и не раскрывать незапрошенные ответы через события |
| Secrets | Не логировать пароль, Wi-Fi credentials из `#S208` и другие чувствительные ответы `scmd` |

## 10. Источники и уровень достоверности

Официально подтверждены:

- адрес `/ws` и авторизация;
- `req_ids` и `req_state`;
- типы `0`, `1`, `2`, `6`, `8`, `10`, `14`, `15`, `16`, `17`, `27` и
  `255`;
- `stype` для типов `0`, `8`, `10` и `16`;
- формат `{id, cmd}` и `cmdres`;
- механизм `scmd` и пример `#S7?`.

Практическими данными конкретного контроллера подтверждены поля ответов для
температурного датчика, аналогового входа, адаптера котла и отопительного
контура, ответ `failed=1`, полный список `req_ids=255`, наблюдаемый FIFO-порядок
типизированных запросов, а также команды `#S4?`, `#S198?`, `#S205?` и `#S208?`.

Не включены как достоверные неподтверждённые списки терминальных команд,
предполагаемые MQTT `#S`-параметры и модели внутренних сервисов.
