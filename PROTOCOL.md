# Локальный протокол ZONT WebSocket

Этот документ объединяет сведения о локальном WebSocket-интерфейсе
контроллеров ZONT, которые используются или исследованы в проекте ZONT Local.
Он не является официальной спецификацией производителя. Поддержка внутренних
команд зависит от модели и версии прошивки.

## Уровни подтверждённости

Для каждой команды указан максимальный достигнутый уровень и основание:

| Уровень | Значение |
| --- | --- |
| **L3 — проверено** | Команда и результат проверены на контроллере H-1V.02 PRO, плата 700, прошивка 625 |
| **L2 — документировано** | Команда описана в официальной документации ZONT, но не проверена в рамках проекта |
| **L1 — клиент** | Команда или формат найдены в официальном веб-клиенте ZONT, его source map либо в Z3K Utility |
| **L0 — гипотеза** | Сведения получены из стороннего кода, косвенного наблюдения или пока не имеют достаточного подтверждения |

`L3` подтверждает поведение только исследованного контроллера и не гарантирует
поддержку другими моделями и прошивками. Если команда имеет несколько
оснований, они перечисляются вместе.

Статический анализ Z3K Utility подтверждает, что официальный клиент умеет
сериализовать или разбирать команду. Он не доказывает, что та же команда
поддерживается через WebSocket конкретным контроллером. Такие сведения остаются
на уровне **L1**, пока не подтверждены документацией или экспериментом.

Обозначения риска:

- **чтение** — не изменяет состояние контроллера;
- **запись** — изменяет состояние объекта или конфигурацию;
- **опасно** — может удалить данные, изменить связь, перезапустить устройство,
  вызвать физическое действие либо расход средств.

## 1. Транспорт и сессия

### 1.1. Подключение и авторизация

Локальный адрес имеет вид `ws://<ip>/ws`. Для TLS может использоваться `wss`,
если его поддерживает конкретная конфигурация контроллера.

| Команда | Ответ | Уровень | Риск |
| --- | --- | --- | --- |
| `{"user":"<username>","pass":"<password>"}` | `{"auth":200}` при успехе, `{"auth":401}` при отказе | **L3**, официальная документация и проверка | запись |

Учётные данные передаются открытым текстом внутри WebSocket. Пароль, имя
пользователя, сетевые идентификаторы и ответы чувствительных системных команд
нельзя выводить в журнал или диагностику.

Контроллер может присылать push-состояния до и после авторизации. До успешного
`auth=200` их нельзя считать состоянием настроенной сессии.

### 1.2. Сопоставление сообщений

В протоколе нет общего ID запроса:

- `ids` соответствует запросу `req_ids`, но не содержит запрошенный тип;
- `scmdres` не содержит исходную команду;
- `cmdres` сопоставляется по `id` или встречавшемуся варианту `Id`;
- объектные push-сообщения могут прийти между запросом и ответом.

Поэтому все запросы постоянного клиента выполняются через общую FIFO-очередь:
следующая команда отправляется только после ответа или ошибки предыдущей.
Ожидание очереди не входит в таймаут ответа, который начинается после
фактической отправки. В одном эксперименте восемь последовательных `req_ids`
получили ответы в порядке отправки, но FIFO со стороны контроллера не является
документированной гарантией.

Входящие push-сообщения не проходят через очередь и обрабатываются сразу.
Запросы, поставленные в очередь на прежнем WebSocket-соединении, после
переподключения не отправляются: актуальные чтения и синхронизация формируются
заново верхними слоями. Односторонняя команда перезапуска занимает очередь
только до завершения отправки, поскольку получение её ответа не гарантировано.

Разрыв соединения отменяет ожидающие ответы. После переподключения временно
неудачные запросы выполняются заново. Ответ `#Sxxx:!` означает отсутствие
данных для конкретной команды в текущий момент и не должен навсегда запрещать
её последующие опросы.

## 2. Базовые JSON-команды

| Команда | Назначение и ответ | Уровень | Риск |
| --- | --- | --- | --- |
| `{"req_ids":<type>}` | Получить `{"ids":[...]}` для типа объекта | **L3**, официальная документация и проверка | чтение |
| `{"req_ids":255}` | Получить общий список известных ID без границ типов | **L3**, официальная документация и проверка | чтение |
| `{"id":<id>,"req_state":0}` | Получить состояние объекта | **L3**, официальная документация и проверка | чтение |
| `{"id":<id>,"cmd":<value>}` | Выполнить команду; результат `{"id":<id>,"cmdres":<code>}` | **L3**, официальная документация и проверка | запись |
| `{"name":"<name>","type":<type>,"cmd":<value>}` | Найти объект по имени либо создать его и выполнить команду | **L3** для типов 0 и 1; **L2** для остальных разрешённых типов | запись |
| предыдущая команда с `"stype":<subtype>` | Создать объект нужного подтипа | **L3** для type 0, stype 19/20; **L2** как общий механизм | запись |
| `{"scmd":"<command>"}` | Выполнить текстовую системную команду; ответ в `scmdres` | **L3**, официальный пример и проверка | зависит от вложенной команды |

`cmdres=0` означает, что команда принята, но не доказывает достижение конечного
состояния. После управляющей команды следует проверить объект через
`req_state` или дождаться подходящего push.

Ответ вида `{"id":<id>,"req_state":0,"failed":1}` означает, что состояние
объекта сейчас недоступно. ID может по-прежнему присутствовать в `req_ids`.
Такой ответ не является ошибкой всего соединения.

`req_ids:255` возвращает только общий набор ID и не сообщает типы объектов.
Тип ранее неизвестного ID определяется отдельным `req_state`. Удаление объекта
можно подтверждать отсутствием ID только в успешно полученном полном списке.

### 2.1. Автосоздание

Официальная MQTT-документация заявляет автосоздание начиная с прошивки 500 для
типов `0`, `1`, `2`, `10`, `14`, `15`, `16`, `17`, `27` и `53` — **L2**.
Практически проверены:

| Команда | Поведение | Уровень | Риск |
| --- | --- | --- | --- |
| `{"name":"HA - Температура","type":1,"cmd":"1 24.1"}` | Создаёт или обновляет виртуальный цифровой датчик температуры | **L3**, также **L2** | запись |
| `{"name":"HA - Контакт","type":0,"stype":20,"cmd":"0 0 180"}` | Создаёт виртуальный НЗ-вход | **L3** | запись |
| `{"name":"HA - Контакт","type":0,"stype":19,"cmd":"0 0 180"}` | Создаёт виртуальный НР-вход | **L3** | запись |

В имени нет стабильного внешнего идентификатора, поэтому перед повторной
настройкой следует привязываться к уже созданному ID, если он известен.

| type 10, stype 3 | `2,N` | Установить аналоговое значение | **L2** | запись |
| mode type 20 | `1` | Применить режим глобально | **L3** через JSON `cmd`, также **L2** | запись |

Для виртуальных type 0 значение `T` является heartbeat: без обновления источник
становится недоступным. Для НЗ (`stype=20`) значения `0` и `20` дают
`trig=0/1`; для НР (`stype=19`) — `trig=1/0`. Это проверено на устройстве.

Команды насоса могут быть приняты, но автоматика контура и настроенный выбег
способны оставить физический выход включённым. Поэтому `cmdres=0` нельзя считать
подтверждением остановки.

## 5. Системные команды `scmd`

### 5.1. Параметры `#S`

Одна таблица объединяет формы чтения, строки `config.txt` и проверенные ответы.
Наличие формата записи в сериализаторе не доказывает, что его безопасно
отправлять как `scmd`.

Парсер `config.txt` официального веб-клиента явно понимает параметры `S7`,
`S12`, `S36`, `S124`, `S180`, `S181`, `S200`–`S204`, `S206`–`S209`, `S211`,
`S212`, `S214`, `S217`, `S218`, `S222`, `S223`, `S225` и `S226`. Остальные
строки `#S` он сохраняет как неизвестные без расшифровки, поэтому их наличие в
прочитанной конфигурации не означает, что клиент понимает их назначение.

| Параметр и форма | Содержимое | Уровень | Риск |
| --- | --- | --- | --- |
| `#S4?` | `#S4:<level> <registration> <operator>` — уровень и регистрация GSM | **L3** | чтение |

## 6. Позиционные структуры `#Z` и `#Y`

### 6.1. Общий синтаксис

Ответы являются позиционными структурами. Внутри встречаются строки в
кавычках и массивы, поэтому обычный `split(',')` неприменим.

Парсер Z3K Utility распознаёт строки по форме
`^#([ZSY])(\d+)([~:=$])(.*)$`, поддерживает вложенные массивы и строки, а
неизвестные строки сохраняет без изменений — **L1**. Это подтверждает общий
синтаксис, но не смысл неизвестных позиций.

### 6.2. Конфигурация объектов `#Z`

Запрос `#Z<id>?` возвращает `#Z<id>:<type>,...` — конфигурацию объекта.
Чтение проверено на контроллере — **L3**, риск — чтение.

Ниже `z[n]` обозначает позицию после номера типа в ответе
`#Z<id>:<type>,z[0],z[1],...`. Таблицы объединяют все найденные схемы независимо
от источника. Имена полей сохранены такими, какими их использует декодер: это
облегчает сопоставление со статическим анализом и не приписывает полям более
точную семантику, чем известно. Схема имеет уровень **L1**, если для неё явно
не указан более высокий уровень.

`rest` означает, что декодер сохраняет все позиции после перечисленных, но не
расшифровывает их. Не все обратные сериализаторы возвращают `rest` в строку.
Пустое или отсутствующее необязательное поле клиент обычно заменяет значением
по умолчанию; это поведение клиента не является требованием wire format.

Официальный интерфейс описывает type 58 как механизм для нестандартных
алгоритмов, например вентиляции. Управляемое им исполнительное устройство не
следует одновременно назначать исполнительным устройством контура отопления;
контур в таком случае может использоваться только как источник уставки —
**L1**. Значения нового объекта по умолчанию: `k_p=0.01`, `k_i=0.01`, `k_d=0`,
`f_0=f_off=f_cutoff=f_min=0`, `f_max=100`, `step_time=1000`, все связи равны
нулю.

Сериализатор type 57 дописывает сохранённый `rest`, а сериализаторы type 58 и
59 формируют только перечисленные именованные позиции. Для type 57 и 59 в
исследованном веб-клиенте нет отдельных декодеров состояния `#Y`.

**Запись `#Z`.** Полный текст конфигурации собирается по следующим правилам —
**L1**:

- объект сериализуется как `#Z<object_id>=<type>,<args>`;
- счётчик следующего ID типа сериализуется как `#Z<packed>=*`, где
  `packed = (type << 12) | counter`;
- неизвестные строки сохраняются без интерпретации;
- строки соединяются последовательностью `CRLF`.

Локальный режим официального веб-клиента читает полную конфигурацию из
`config.txt`, а при сохранении записывает файл целиком и отправляет
`CFG_RELOAD`. Входящая одиночная строка `#Z<id>=...` применяется к уже
загруженной конфигурации как точечный push. Поэтому наличие сериализатора
`#Z` не означает, что интерфейс сохраняет настройки последовательностью
отдельных команд `#Z` — **L1**.

| Команда | Назначение | Уровень | Риск |
| --- | --- | --- | --- |
| `#Z<object_id>=<type>,...` | Создать или заменить конфигурацию объекта | **L1** | **опасно, изменение конфигурации** |
| `#Z<packed>=*` | Сохранить счётчик следующего ID типа; `packed = (type << 12) \| counter` | **L1** | **опасно, изменение конфигурации** |
| `#Z<object_id>~` | Удалить объект | **L1** | **опасно, удаление данных** |

Известный частный пример создания радиобрелока:
`#Z<object_id>=29,'<name>'` — **L1**. Наличие сериализатора подтверждает формат,
но не транспорт записи, допустимость значений или поддержку операции
конкретной прошивкой.

### 6.3. Состояние объектов `#Y`

Запрос `#Y<id>?` возвращает `#Y<id>$...` — оперативное внутреннее состояние.
Чтение проверено на контроллере — **L3**, риск — чтение.

Ниже `y[n]` обозначает позицию после `$` в ответе
`#Y<id>$y[0],y[1],...`. Таблица объединяет все известные декодеры и наблюдения.
Отсутствие типа не означает отсутствие `#Y`: формат может быть не расшифрован.

Официальный локальный клиент получает начальный снимок и затем раз в минуту
повторяет адресные `#Y<id>?` для известных из конфигурации объектов типов `0`,
`1`, `2`, `6`–`8`, `10`, `14`–`17`, `20`, `27`, `31`, `35`, `37` и `53`.
Ответы разбираются по типу объекта и по одному объединяются со снимком по ID.
Для type 58 библиотечный декодер `#Y` существует, но в периодический список
исследованной версии веб-клиента этот тип не включён — **L1**.

| `#Y<circuit_id>=,,,<temperature_dk>` | Альтернативная ветвь установки температуры | **L1**, семантика условия неясна | запись |
| `#Y<scenario_id>=1` | Запустить сценарий | **L1** | опасно, зависит от сценария |
| `#Y<prev_module_id>=*,0`, затем `#Y<module_id>=*,120` | Добавить радиодатчики | **L1** | опасно, радиоконфигурация |
| `#Y<fob_id>=0/1` | Разрешить или запретить добавление кнопок брелока | **L1** | запись |
| `#Y<module_id>=*,*,0/1` | Разрешить или запретить добавление датчиков 433 МГц | **L1** | запись |
| `#Y<object_id>=255` | Очистить радиомодуль | **L1** | **опасно, удаление данных** |
| `#Y<zone_id>=<onguard>` | Изменить охрану зоны | **L1** | опасно, физическая охрана |
| `#Y<element_id>=<state>[,<value>]` | Изменить веб-элемент | **L1** | запись |
| `#Y<analog_output_id>=3,<value>` | Изменить значение аналогового выхода | **L1**, Z3K Utility | опасно, физический выход |
| `#Y<object_id>=0..3` | Нормальное/тестовое состояние насоса или реле | **L1** | опасно, физический выход |
| `#Y<tap_id>=*,0/1` или `#Y<tap_id>=*,255` | Тест смесителя либо выход из теста | **L1** | опасно, физический выход |
| `#Y<object_id>=0/1` | Запустить или остановить калибровку | **L1** | опасно |
| `#Y<object_id>=16/0` | Разрешить или запретить внешнюю панель | **L1** | запись |

Z3K Utility формирует ручную уставку как
`int((temperature_celsius + 273) * 10)`. Это преобразование использует
усечение, а не округление — **L1**.

В исследованном веб-клиенте сериализатор `ChangeAnalogOutputValue` возвращал
пустой список, тогда как Z3K Utility 2.72.0 формирует
`#Y<analog_output_id>=3,<value>`. Поддержка команды конкретным контроллером не
проверена, поэтому максимальный уровень остаётся **L1**.

## 7. Push-сообщения и обновление конфигурации

Контроллер отправляет JSON push в том же формате, что и `req_state`. Проверены
push для контуров, реле, смесителя, пользовательских элементов, температурных
и аналоговых датчиков — **L3**. Push охранной зоны не наблюдался: изменение зоны
надёжно подтверждается адресным `req_state`.

Бинарный push вида `#Y<id>$...` наблюдался при изменениях контуров и смесителя.
При создании объекта приходил `#Z<id>=...`, а следующая свободная позиция могла
обозначаться `#Z<id>=*` — **L3**. В JSON-режиме отдельный входящий
`CFG_RELOAD_REQ` поймать не удалось.

`SCFG_RELOAD_REQ?` проверен как активный запрос перечитывания конфигурации, а не
как пассивное уведомление. `SGETALLSTATES?` возвращает только счётчик и не
заменяет `req_ids`, `req_state`, `#Y` или `#Z`.

## 8. Кратко о бинарном режиме

Официальный локальный клиент умеет передавать текстовые команды бинарными
WebSocket-кадрами. Например, бинарная строка `#Y<id>?` получает бинарный ответ
`#Y<id>$...`. Это проверено на устройстве — **L3**. JSON-обёртка `scmd`
предоставляет доступ к тем же текстовым командам и используется интеграцией.

Официальная документация также описывает бинарный файловый протокол:

| Код запроса/ответа | Операция | Уровень | Риск |
| --- | --- | --- | --- |
| `0x40 / 0x41` | Открыть файл | **L2** | чтение или запись |
| `0x42 / 0x43` | Закрыть файл | **L2** | запись |
| `0x44 / 0x45` | Записать блок с подтверждением | **L2** | опасно, изменение файлов |
| `0x46 / 0x47` | Записать блок без подтверждения | **L2** | опасно, изменение файлов |
| `0x48 / 0x49` | Прочитать блок | **L2** | чтение |
| `0x4A / 0x4B` | Получить список файлов | **L2** | чтение |
| `0x4C / 0x4D` | Удалить файл | **L2** | **опасно, удаление данных** |
| `0x4E / 0x4F` | Создать каталог | **L2** | запись |
| `0x56 / 0x57` | Форматировать файловую систему | **L2** | **опасно, потеря данных** |

Интеграция не использует файловый протокол. Форматирование, удаление и запись
файлов не должны становиться универсальными действиями Home Assistant.

## 9. Правила безопасной реализации

- Сериализовать `req_ids` и `scmd`, потому что ответы не содержат достаточной
  корреляции.
- Различать `ids`, `cmdres`, `scmdres`, объектные состояния и push.
- После `cmdres=0` проверять фактическое состояние объекта.
- Не считать `failed=1`, `#Sxxx:!` или таймаут отдельной команды отказом всего
  контроллера.
- После переподключения повторять нужные чтения и полный контрольный опрос.
- Не публиковать необработанные `scmdres`: они могут содержать пароли, номера,
  координаты, сетевые адреса и идентификаторы оборудования.
- Не предоставлять команды удаления, конфигурации сети, радиомодуля,
  файловой системы, звонков и SMS без отдельного безопасного сценария.
- Не считать наличие команды или сериализатора в официальном клиенте
  доказательством поддержки той же операции через WebSocket и конкретной
  прошивкой контроллера.
- Не приписывать неизвестным позиционным полям смысл без воспроизводимого
  эксперимента или подтверждения официальным источником.
