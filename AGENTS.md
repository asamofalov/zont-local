# Правила работы с проектом

## О проекте

ZONT Local — пользовательская интеграция Home Assistant для локального
WebSocket-интерфейса контроллеров ZONT.

- Домен интеграции — `zont_local`.
- Исходный код — `custom_components/zont_local`.
- Автоматические тесты — `tests`.
- Среда разработки — `.devcontainer`.
- Минимальная поддерживаемая версия Home Assistant — 2026.3.0, текущая версия
  среды разработки и основного набора тестов — 2026.8.0.
- Интеграция представляет один локальный hub, использует `local_push`, одну
  config entry и один постоянный WebSocket-клиент.

## Источники истины

Не дублируйте одно и то же описание в нескольких документах:

- `README.md` описывает пользовательское поведение, установку, настройку и
  публичные возможности;
- `PROTOCOL.md` содержит известные команды, форматы, уровни подтверждённости и
  риски протокола ZONT;
- `ARCHITECTURE.md` фиксирует границы слоёв, поток данных, владение ресурсами и
  жизненный цикл интеграции;
- `ROADMAP.md` содержит планы и статус будущих этапов.

README, roadmap, архитектурная и протокольная документация, локализация и
пользовательские тексты ведутся на русском языке. Идентификаторы Python, имена
файлов, ключи протокола и другие технические интерфейсы сохраняйте в принятом
для них формате.

Исключение — обязательный английский fallback
`custom_components/zont_local/translations/en.json`. Он должен полностью
повторять структуру `ru.json`, включая placeholders. Для custom integration не
создавайте `strings.json` и не используйте build-time ссылки `[%key:...%]`.
Названия и описания действий размещайте в разделе `services` обоих файлов
переводов, а в `services.yaml` оставляйте только схему полей и selectors.

Обновляйте документацию вместе с поведением, которое она описывает. Изменение
границ, потока данных или порядка запуска и выгрузки требует актуализации
`ARCHITECTURE.md`. Изменение публичного поведения требует актуализации README.

## Архитектура

Перед изменением слоёв, жизненного цикла или владения ресурсами прочитайте
`ARCHITECTURE.md`. Следуйте актуальной документации разработчика Home Assistant
и применимым правилам Integration Quality Scale:
<https://developers.home-assistant.io/docs/core/integration-quality-scale/>.

- Предпочитайте штатные механизмы, helpers и жизненный цикл Home Assistant
  собственной инфраструктуре. Отступление должно иметь техническую причину,
  которую можно объяснить в коде или документации.
- Сохраняйте однонаправленную зависимость адаптеров Home Assistant от пакета
  `protocol`. Код `protocol` не должен импортировать Home Assistant или
  обращаться к сущностям, реестрам и config entry.
- Передавайте внешние ресурсы явно. Одна config entry владеет одним постоянным
  клиентом, а объект, создавший задачу, callback или подписку, освобождает её.
- Передавайте состояние как целостный неизменяемый снимок. Один владелец
  обновляет данные, потребители не изменяют их и не наблюдают частично
  применённое обновление.
- Держите `async_setup_entry` платформ и config flow тонкими: они связывают
  штатные механизмы Home Assistant с предметной логикой, но не реализуют её.
- Не выполняйте блокирующие операции в event loop. Используйте рекомендованные
  Home Assistant способы их изоляции:
  <https://developers.home-assistant.io/docs/asyncio_blocking_operations/>.
- Временная недоступность должна восстанавливаться автоматически. Ошибки
  авторизации должны запускать понятный reauthentication flow, а повторяющиеся
  сбои не должны засорять журнал.
- Не закрепляйте решение только потому, что так устроена текущая реализация.
  При изменениях выбирайте принятый в экосистеме Home Assistant подход.

## Работа с протоколом

`PROTOCOL.md` — единственный свод знаний о протоколе ZONT. Если для реализации
не хватает сведений, сначала зафиксируйте результат исследования в нём.

- Для каждой новой команды указывайте уровень подтверждённости `L0–L3`,
  источник сведений и риск операции.
- Не выдавайте гипотезу или наличие сериализатора в официальном клиенте за
  подтверждённую поддержку контроллером.
- Неподтверждённые, разрушающие или способные нарушить связь команды не должны
  становиться публичным поведением без отдельного решения, защитных мер и
  автоматических тестов.
- Обезличивайте примеры и исследовательские записи. Не сохраняйте реальные
  учётные данные, сетевые адреса, номера, координаты, серийные номера и другие
  чувствительные значения.
- Разделяйте знание о wire format и адаптацию к Home Assistant. Сначала
  моделируйте и проверяйте протокол, затем создавайте сущности и UI.

## Среда разработки

Основная среда — devcontainer из `.devcontainer/devcontainer.json`. Откройте
репозиторий командой **Dev Containers: Reopen in Container** и выполняйте
проектные команды внутри контейнера. Зависимости закреплены в
`requirements_test.txt` и устанавливаются `postCreateCommand`.

Не создавайте `.venv` и не устанавливайте зависимости проекта на хосте.

Для запуска локального Home Assistant используйте:

```bash
python -m homeassistant --config .devcontainer/config
```

Runtime-данные из `.devcontainer/config`, включая базы данных, журналы и
lock-файлы, не должны попадать в репозиторий. Не добавляйте секреты в код,
тесты, журналирование, диагностику или документацию.

## Совместимость и версия

Сохраняйте пользовательскую конфигурацию и публичные контракты: домен, формат
config entry, `unique_id`, entity ID, действия и события. Если совместимость
сохранить нельзя, добавьте явную миграцию и опишите изменение для пользователя.

Версию в `custom_components/zont_local/manifest.json` повышайте для
пользовательского функционального релиза. Не повышайте её для изолированного
изменения документации, тестов, `AGENTS.md` или рефакторинга без изменения
поведения.

## Проверки

Добавляйте или обновляйте тесты для изменённого поведения. Существенные
изменения протокола проверяйте на уровне чистого пакета `protocol`, а адаптацию
к Home Assistant — отдельно.

Перед завершением изменения выполните внутри devcontainer:

```bash
python -m pytest -q --cov=custom_components.zont_local --cov-report=term-missing
ruff check .
ruff format --check .
python -m homeassistant --script check_config --config .devcontainer/config
```

Минимальную поддерживаемую версию Home Assistant проверяйте в отдельном
временном окружении внутри devcontainer:

```bash
(
  min_ha_env=$(mktemp -d /tmp/zont-ha-2026.3.0-XXXXXX)
  min_ha_config=$(mktemp -d /tmp/zont-ha-config-XXXXXX)
  trap 'rm -rf "$min_ha_env" "$min_ha_config"' EXIT
  python -m venv "$min_ha_env"
  "$min_ha_env/bin/python" -m pip install -r requirements_test_min.txt
  "$min_ha_env/bin/python" -m pip install --no-deps --force-reinstall homeassistant==2026.3.0
  "$min_ha_env/bin/python" -c 'from importlib.metadata import version; assert version("homeassistant") == "2026.3.0"'
  "$min_ha_env/bin/python" -m pytest -q
  mkdir -p "$min_ha_config/custom_components"
  cp .devcontainer/config/configuration.yaml "$min_ha_config/configuration.yaml"
  sed -i '/^default_config:$/d' "$min_ha_config/configuration.yaml"
  ln -s "$PWD/custom_components/zont_local" "$min_ha_config/custom_components/zont_local"
  "$min_ha_env/bin/python" -m homeassistant --script check_config --config "$min_ha_config"
)
```

Hassfest запускайте на хосте через официальный контейнер с каталогом проекта,
подключённым только для чтения:

```bash
docker run --rm -v "$PWD:/github/workspace:ro" ghcr.io/home-assistant/hassfest
```

Workflow-файлы GitHub Actions проверяйте на хосте через официальный контейнер
actionlint:

```bash
docker run --rm -v "$PWD:/repo:ro" --workdir /repo rhysd/actionlint:1.7.12 -color
```

Не исправляйте посторонние изменения в рабочем дереве. Перед передачей
результата проверьте `git diff --check` и убедитесь, что в diff нет runtime-файлов
или секретов.
